- **Firebase connection/CLI:** Firebase is marked installed and connected in the app, but this execution session exposes no Firebase project inspection tools. The local CLI is present, yet `firebase --version` and `firebase projects:list --json` both stop before running with `EPERM` opening `C:\Users\HomePC\.config\configstore\firebase-tools.json`. No account state was retrieved and no credential contents were read.
- **Public form write exposure:** `firestore.rules` permits unauthenticated client `create` operations in `supportRequests` and `partnershipRequests` after schema/length/timestamp validation. There is no per-client or per-IP rate limiting in these rules; frontend writes go directly through Firestore (`src/firebase/submissions.ts`). This is a code-level abuse/cost and inbox-spam risk, not evidence of an incident. Consider App Check enforcement for Firestore plus server-side throttling/abuse controls, preserving intended public form access. Deployed App Check enforcement remains unknown.
- **Rule protections reviewed:** own-profile and application reads are UID-scoped; application reviews are admin-only and coupled atomically; memberships and payment/certificate writes are denied to clients; chat reads are owner/admin scoped; catch-all Firestore access denies. Storage writes are admin-only, validate metadata/size/content type, and unmatched paths deny. These are source findings only; the Firestore/Storage rules emulator suite has not been run in this environment and live rules remain unverified.
- **App Check startup behavior:** web client initializes App Check only when `VITE_FIREBASE_APPCHECK_SITE_KEY` is present; the Pages workflow sources this from a GitHub variable. Missing/invalid variable means the client will not initialize App Check. The repository does not establish whether the variable is set or Firestore/Storage/Functions enforcement is enabled remotely.
- **Read-only verification:** no project listing, Functions listing, deployed rules, secret metadata, App Check enforcement, or billing plan could be inspected. No backend fix or deployment was attempted. Source-level rules observations do not alter the earlier 404 evidence or establish what is currently deployed.

**Immediate backend code concern:** unrestricted public writes to two PII-bearing Firestore inbox collections can be automated at low effort because the rules validate content but impose no request budget.
